    Deployment and releases¶

    Alcazaba is released from GitHub Actions: a vX.Y.Z tag builds the distributions, generates the SBOM, signs everything with Sigstore (no keys to keep), publishes to TestPyPI, checks that version installs, and publishes to PyPI after a manual approval. The repository is nonodev96/fastapi-alcazaba.

    One-time setup¶

    1. Repository¶

    git remote add origin git@github.com:nonodev96/fastapi-alcazaba.git
git push -u origin main

    The project URLs in pyproject.toml already point to it.

    2. Repository settings¶

    • Actions → General → Workflow permissions: read repository contents (the workflows ask for more per job).
    • Rules → Rulesets:
      • main: block force pushes and deletion, require a linear history. With a single maintainer pushing to it; with more, require a pull request and the status checks of CI (Lint and type check, Unit and integration tests (3.11) … (3.14), End-to-end, Package, Audit dependencies, Docs) too.
      • Tags v*: block updates and deletion (a published version must never move), and only the repository's admins create them (a second ruleset, so that their bypass is for creating only).
    • Environments:
      • testpypi: deployment tags v*.
      • pypi: deployment tags v*, required reviewer: you (the approval before PyPI).
      • github-pages: created when Pages is enabled; deployment branch main, from which the Docs workflow deploys every version.
    • Pages: source "GitHub Actions". The Docs workflow keeps a site per version in the gh-pages branch, which its first run creates: dev for main, X.Y for each release.
    • Security: Dependabot alerts and security updates, secret scanning with push protection, private vulnerability reporting (SECURITY.md points there), code scanning (CodeQL and Scorecard upload their results).

    3. Trusted publishers¶

    Before the first release the project doesn't exist on the indexes: add a pending publisher on TestPyPI and on PyPI:

    Field TestPyPI PyPI
    PyPI project name fastapi-alcazaba fastapi-alcazaba
    Owner nonodev96 nonodev96
    Repository fastapi-alcazaba fastapi-alcazaba
    Workflow release.yml release.yml
    Environment testpypi pypi

    No API token is created or stored anywhere: the workflow proves its identity with OIDC.

    Releasing¶

    1. Move the Unreleased notes of CHANGELOG.md under ## [X.Y.Z] - YYYY-MM-DD and merge to main; wait for CI.

    2. Tag the merge commit on main and push the tag:

      git switch main && git pull
git tag vX.Y.Z
git push origin vX.Y.Z

    3. The Release workflow:

      1. checks that the tag is a version on main and runs every suite;
      2. builds the sdist and the wheel (the version comes from the tag, SOURCE_DATE_EPOCH from the commit);
      3. generates the CycloneDX SBOM and validates it;
      4. signs: GitHub attestations of build provenance (SLSA) and of the SBOM, plus a Sigstore bundle per file;
      5. publishes to TestPyPI and installs that version in a clean environment (smoke test);
      6. waits for your approval in the pypi environment, then publishes to PyPI with PEP 740 attestations;
      7. creates the GitHub release with the distributions, the SBOM, the provenance, the Sigstore bundles and the notes of that version from the changelog;
      8. runs the Docs workflow, which publishes the documentation of the release as X.Y, with the latest alias that the root of the site leads to.

    Pre-releases (vX.Y.ZrcN, aN, bN) stop after TestPyPI and become GitHub pre-releases, with no documentation of their own. They take the changelog section of the version they lead to (v0.1.0rc1 → ## [0.1.0]), which can still say Unreleased: a first rc tries the whole pipeline without spending the version.

    If something goes wrong¶

    • Nothing reaches PyPI until you approve it: reject the deployment and fix.
    • A version can't be uploaded twice. Published something broken? Yank it on PyPI (it stays installable only when pinned exactly) and release X.Y.Z+1.
    • Don't move or reuse a tag that was released.
